# 项目决策记录

更新日期：2026 年 11 月 16 日。

本文区分当前讨论方向、技术建议和待确认信息，避免把示例或建议误当成已经落实的业务事实。

## 当前规划方向

| 事项 | 当前方向 | 理由 |
| --- | --- | --- |
| 问题来源 | 个人微信业务群 | 用户已说明实际使用场景 |
| 团队入口 | 独立网页 | 支持业务同事共同使用 |
| 处理规则 | 收录、分析、追问规则独立维护，按需要封装为 Skill | 固定流程和第三期 Agent 可以复用 |
| 第一期 | 手动录入、案例库、固定 AI 流程、人工确认 | 先验证经验整理和复用是否有效 |
| 第二期 | 本地工具辅助采集，先验证一键收集，再评估定时采集 | 逐步减少手动复制，实际能力取决于客户端验证 |
| 第三期 | 自建业务排查 Agent | 在已有数据和接口上增加动态追问和多步工具使用 |
| 衔接基础 | 前两期落实接口、完整数据、独立规则和评估样本 | 降低第三期重复建设的工作量 |

## 已提出的技术建议

建议采用 React＋TypeScript＋Vite 前端，Python＋FastAPI 后台，PostgreSQL 数据库；语义检索按效果引入 pgvector，后台耗时任务按需使用 Celery＋Redis。第三期评估采用 LangGraph，微信采集工具独立部署在登录微信的电脑上。

这是当前推荐方案，尚未确认开发人员的语言经验、部署环境、具体依赖版本和模型服务。选择依据和职责划分见完整规划文案。

## 待确认事项

- 首个试点业务与实际问题样本。
- 试用人数、实际使用者和方案确认人。
- 数据在不同业务之间的可见范围与维护责任。
- 公司已有的登录、开发和部署基础。
- 可使用的模型服务，以及中文、截图提取和检索的样本效果。
- 采集电脑、微信版本与可获取的消息范围。
- 第一阶段投入、工期及运维责任。

## 实施时需要继续遵守的约定

- AI 生成的方案先作为草稿，实际验证和发布由对应人员确认。
- 模型与 Skill 规则不能替代服务端的权限和状态校验。
- 原始依据、案例和运行记录分别保存，并以稳定编号关联。
- 新问题的结案材料不能提前泄露到该问题的历史回放评估中。
- 第三期 Agent 复用已实现的能力；新增业务系统访问需要实际开发对应工具。
