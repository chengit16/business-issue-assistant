**业务问题与解决方案平台｜规划文案（讨论稿）**

版本：0.4　日期：2026 年 11 月 16 日

本文按“个人微信群是问题来源、业务同事通过独立网页使用、团队内部共享”规划。产品名称暂定为“业务问题助手”。试点人数、案例数量和验收目标均为建议值，待真实样本验证。

**项目介绍文案，可用于内部提案。**

我们计划建设一个面向业务团队的“业务问题助手”，将分散在微信群里的问题、排查过程和解决经验，整理为可查询、可追溯、可持续更新的团队案例库。

业务同事遇到问题时，可以在网页中输入描述或粘贴截图，AI 会结合历史案例，提供相关处理经验、建议的排查步骤，以及仍需补充的信息。问题解决后，处理人补充实际操作和处理结果，AI 再协助整理成案例，经确认后供团队复用。

平台通过统一的收录与分析规则，减少重复整理和重复答疑，让业务经验从个人记忆逐步沉淀为团队共享的知识。第一阶段从一个高频业务场景试点，重点验证历史经验是否能帮助同事更快找到处理方法，再逐步扩展到更多业务群。

**要解决的具体问题。**

业务群数量增加后，同类问题会在不同群里反复出现；问题描述和最终结论散落在多段对话里，查找成本高；熟悉业务的同事承担大量重复答疑，新同事也难以判断旧方案是否仍适用。平台需要同时解决“经验收集”和“经验使用”，并把每次实际处理结果补回案例库。

第一版围绕三个目标设计：让同事找到相关案例，让处理建议有依据，让有效经验能够持续更新。实际收益通过试点衡量，不预先承诺回答准确率或节省比例。

**使用者与日常分工。**

| 角色 | 主要操作 | 日常责任 |
| --- | --- | --- |
| 业务同事 | 提问、上传材料、查看案例、反馈结果 | 提供必要背景，反馈建议是否有效 |
| 问题处理人 | 补充排查过程、实际措施和处理结果 | 确认本次问题是否解决，以及哪些措施被验证有效 |
| 知识维护人 | 发布案例、合并重复项、修订过期方案 | 维护案例质量和适用范围，可由业务负责人兼任 |

建议试点业务指定一名知识维护人，在固定时间处理待确认案例。AI 负责降低整理成本，业务人员负责确认业务事实。

**一次完整的使用过程。**

1. 业务同事在微信群里遇到问题，打开平台，粘贴问题描述、相关聊天或截图，选择所属业务。
2. AI 提取问题现象、关键时间、报错信息和已尝试的操作。识别不清的截图文字保留为待确认信息，避免错误码、金额或编号被误读。
3. 系统在用户可访问的案例中检索，优先展示适用条件匹配、方案已验证的历史案例。
4. AI 给出当前问题的理解、相关案例、适用条件差异、建议排查顺序和待补充信息。关键条件缺失时，先提出少量必要追问。
5. 同事根据建议自行处理或转交问题处理人，并可复制一段简短回复回到微信群。
6. 处理人反馈“已解决、仍未解决、方案不适用”，补充实际操作及结果。
7. AI 生成案例新增或修订草稿，处理人确认验证结果，知识维护人确认发布。后续相似提问即可引用这次经验。

提问记录和正式案例分别保存：每次提问都保留上下文，只有具备复用价值的内容才整理成案例，避免大量重复提问淹没知识库。

**页面结构与核心文案。**

业务同事进入平台后，首页直接展示提问输入框，并提供“收录经验”入口。电脑端和手机浏览器共用同一套流程。

| 页面或视图 | 主要内容 | 用户可执行的操作 |
| --- | --- | --- |
| 问题助手 | 问题输入、图片附件、业务选择、分析结果、来源案例 | 提问、补充信息、复制回复、保存问题、反馈结果 |
| 收录经验 | 原始聊天与 AI 整理草稿并排展示、相似案例提示 | 校正内容、补充方案、选择新增或修订、提交确认 |
| 案例库 | 搜索、业务分类、适用条件、验证状态、案例详情 | 查看步骤及原始依据、反馈方案失效、复用案例 |
| 我的记录与待确认 | 我的提问、待补充材料、待确认草稿、待修订案例 | 跟进问题、确认结果、发布或退回草稿 |

首页主标题：“遇到业务问题，先查团队经验。”

首页说明：“输入问题或粘贴截图，查找历史案例，获取有依据的排查建议。”

输入框提示：“描述发生了什么、涉及哪个业务、已经尝试过哪些操作，也可以直接粘贴群聊内容。”

收录入口：“把这次解决经验留下来。”

收录说明：“粘贴问题和处理过程，AI 帮你整理；确认后，团队下次可以直接查找。”

无匹配结果：“暂未找到适用的已验证案例。你可以补充以下信息，或将问题保存后交由处理人继续跟进。”

结果反馈：“已解决”“仍未解决”“方案不适用”。

以上界面使用业务语言；RAG、向量检索、Skill 等实现概念放在开发方案和后台配置中。

**案例库保存什么。**

每条案例应同时保存“便于复用的整理结果”和“可核对的原始依据”。

| 信息 | 内容 |
| --- | --- |
| 问题概况 | 标题、问题现象、业务分类、常见不同问法 |
| 适用条件 | 涉及的系统、渠道、版本、时间范围及其他业务前提 |
| 排查记录 | 已尝试的操作、观察结果、已排除的原因 |
| 原因与方案 | 已确认根因或待验证假设、处理步骤、执行角色和前置条件 |
| 验证结果 | 谁在什么条件下验证，执行了什么操作，结果如何 |
| 原始依据 | 保存的聊天片段、图片、材料编号及对应引用位置 |
| 维护信息 | 负责人、创建和更新时间、变更记录、替代案例 |

原始依据链接到平台内保存的材料，不依赖个人微信能够提供某条消息的可访问链接。原文存在分歧时，保留不同说法及确认结果，不用一段总结覆盖全部证据。

状态分成三个独立维度，避免“问题解决了”被误解为“根因和方案都已验证”：

- 问题进度：待处理、处理中、已解决、重新打开。
- 案例发布：草稿、待确认、已发布、已归档。
- 方案有效性：待验证、已验证、已失效。

已解决的问题可以暂时没有已验证根因。待解决问题也可以作为已发布记录供协作，但不能作为已验证解决方案引用。单次使用失败先保留反馈，由维护人判断是适用条件不同还是方案确实失效。

**Skill 如何支撑这个产品。**

Skill 用于封装可复用的任务规则、步骤、模板与示例；数据库读写和权限控制由应用服务承担。这与 OpenAI Docs 对 Skill 和工具服务的职责划分一致，参见 [OpenAI Docs：Skills](https://developers.openai.com/plugins/concepts/skills)。

本项目建议先围绕两个任务组织规则包，结案整理复用收录规则：

| 规则包 | 输入 | 核心规则 | 输出 |
| --- | --- | --- | --- |
| 案例收录与更新 | 原始材料、已有案例、处理反馈 | 分清事实与猜测；缺失信息留空；检查重复；保留验证依据 | 结构化草稿、缺失字段、引用位置、新增或修订建议 |
| 问题分析与回答 | 新问题、补充上下文、检索到的案例 | 比较适用条件；引用来源；区分历史结论与本次推测；不足时追问 | 案例匹配说明、排查建议、待补充信息、简短回复草稿 |

网页后台根据用户点击的操作调用对应流程，加载规则包、调用检索工具和模型，再校验输出。业务同事通过网页使用这些能力，不需要各自在电脑上安装 Skill。

开发时可把规则和模板维护为版本化文件，并按需要封装为兼容的 Skill。普通模型接口不会因为项目里存在一个 `SKILL.md` 就自动执行其中的流程，需要后台明确加载或使用支持 Skill 的运行环境。

规则版本应随分析记录保存，便于定位回答变化。引用必须指向实际存在且用户有权访问的材料；发布权限、可见范围、必填字段和状态转换由服务端代码校验。

**系统如何检索和分析。**

整体组成可概括为：独立网页、应用后台、案例与原始材料存储、检索服务、模型服务、Skill 规则包。

网页发起提问后，后台先确认用户的业务范围，再结合关键词、语义相似度和适用条件检索案例，读取候选案例的完整处理步骤及依据，最后让模型生成分析结果。

错误码和系统名称适合精确查找，不同表达但含义相近的问题适合语义检索，业务范围与版本用于筛选。向量索引是检索的辅助数据，案例正文、验证记录和来源仍存放在持久化数据库与文件存储中。

从技术分类看，这属于结合结构化案例的检索增强生成，也就是 RAG。Skill 规定处理流程，检索负责找到资料，模型负责理解和表达，案例库负责保存团队经验。

第一版可以从关键词和条件检索起步，用真实问题检验召回效果；如果不同说法造成明显漏检，再补充向量检索。新案例或方案状态更新后，检索索引要同步更新；返回答案前仍以数据库中的当前状态为准。

模型调用在后台执行，团队账号和业务权限同时约束案例、原始附件及检索结果。故障时保留用户输入和草稿，提供重试入口，避免重复提交生成多条相同记录。

**答案应当是什么样。**

以下为展示格式的虚构示例，不代表已经存在的案例或可直接执行的支付操作建议。

用户输入：“客户已经扣款，但订单还显示待支付。”

系统回答：“你描述的是支付结果与订单状态不一致。历史案例 A 也出现过这一现象，已确认原因是支付结果同步延迟，但它适用于渠道甲；当前问题的支付渠道和发生时间尚未提供，因此目前只能作为排查参考。建议先补充订单编号、支付渠道及发生时间，由有权限的处理人核对支付流水和订单记录。原始处理记录见案例 A。”

页面提供“查看案例”“补充信息”“复制回复”“记录处理结果”。案例适用性用具体差异说明，第一版不展示缺乏校准依据的“置信度 95%”一类数值。

**第一版交付范围。**

第一版包含：团队登录、基础业务权限、文字和截图录入、AI 整理草稿、案例确认发布、检索与辅助分析、来源引用、处理结果反馈、案例修订与失效管理。

个人微信群采用用户主动粘贴内容或上传截图的方式接入，平台生成回复草稿后由同事自行复制发送。这样可以直接验证整理和问答的价值，消息接入自动化再根据试点需求单独评估。

复杂工单流转、自动执行业务操作、跨系统数据查询、全量聊天导入和群内自动回复列为后续候选能力，不纳入首轮验收。正式的权限检查和必要操作前提仍应随方案记录清楚。

**推进顺序与验收方式。**

| 阶段 | 主要工作 | 进入下一阶段的条件 |
| --- | --- | --- |
| 样本整理 | 选择一个高频业务，收集约 50–100 条典型记录，统一字段和确认规则 | 能区分问题、处理方案及其验证依据，确定知识维护人 |
| 最小版本 | 打通录入、整理、确认、检索、回答、反馈和修订 | 能用真实样本完整演示一次解决经验被再次使用 |
| 小范围试点 | 邀请约 5–10 名同事，围绕 1–2 个群的业务试用，建议观察两周 | 获得足够的真实提问、处理反馈和失败样本 |
| 效果复盘 | 修正规则、字段和检索方式，再决定扩展业务范围 | 证明检索可用，维护负担可接受，业务同事愿意持续使用 |

建议准备 30 条固定评估问题：其中 10 条有已知案例且改变提问方式，10 条现象相似但适用条件不同，10 条没有已有答案或关键背景不足。历史案例可以作为知识来源；回放真实新问题时，以提问时间为截点，只提供当时可用的资料，排除该次问题事后生成的结案记录，避免提前泄露答案。

试点验收目标建议设为：

- 对已知案例问题，前 5 条检索结果命中对应有效案例的比例达到 80% 以上；这是试点目标，不是系统已有能力。
- 抽查答案中作为依据的关键结论，引用能打开、内容能够支持结论，且引用资料在当前用户权限范围内。
- 对适用条件不一致、方案已失效和没有答案的样本，系统能明确指出差异或信息缺口，不把历史方案直接当作本次结论。
- AI 草稿在人工确认前保持未验证状态；失效、归档或无权访问的材料不会继续作为有效方案推荐。
- 记录“首次获得有用建议的时间”“收录一条案例所需的人工时间”“反馈已解决的提问占比”，与试点前同类问题的实际处理情况比较。已解决反馈不能单独证明 AI 的贡献，需要抽样复盘。

开发排期在样本梳理后估算，主要取决于现有登录体系、部署环境、可用模型服务和图片处理需求。试点期间同时记录模型调用成本、响应时间和知识维护工时，为后续投入提供依据。

**建议技术选型与分期引入。**

本建议按“小团队开发、团队内部使用、目前没有必须沿用的技术栈”选择，作为待确认的实施方案。若已有成熟前端、登录体系或后台服务，应结合维护人员的经验调整，优先复用已有基础。

核心组合为 React＋TypeScript＋Vite 前端、Python＋FastAPI 后台、PostgreSQL 数据库和文件存储。后台按业务模块组织，接口与后台任务共享业务服务逻辑。第三期再接入 Agent 编排运行时。

| 层次 | 建议技术 | 用途与引入时机 |
| --- | --- | --- |
| 业务页面 | React、TypeScript、Vite；界面组件使用 Ant Design | 第一期建设提问、收录、案例库和待确认视图，适配电脑及手机浏览器 |
| 后台接口 | Python、FastAPI、Pydantic | 第一期提供 HTTP 接口，定义输入输出结构，校验模型提取结果；通过 OpenAPI 描述接口契约 |
| 数据管理 | PostgreSQL、SQLAlchemy、Alembic | 第一期保存业务记录、来源关系和运行记录，用数据库迁移维护字段变化 |
| 语义检索 | PostgreSQL 的 pgvector 扩展 | 先落实字段筛选与精确查询，根据真实样本引入语义检索，并与关键词检索组合 |
| 原始文件 | 云对象存储，按部署环境选择兼容接口；本地开发可用文件目录 | 保存截图、附件和导入材料，数据库保存文件引用与版本；开发与生产使用同一文件访问抽象 |
| 模型调用 | 模型供应商 SDK 或 HTTP 客户端，统一封装模型适配层 | 第一期根据中文提取、图片理解和结构化输出的真实样本选服务，向量化使用单独的嵌入模型接口 |
| 后台任务 | Celery＋Redis | 正式试点涉及耗时导入、图片处理和索引更新时引入；第二期复用服务端任务处理能力。任务最终状态保存在 PostgreSQL |
| 微信采集 | 本地采集适配器＋HTTPS 平台接口 | 第二期按实际电脑和微信版本验证实现；采集端与平台采用独立的接口契约 |
| Agent 编排 | LangGraph，配置持久化检查点 | 第三期用于多步任务、追问等待和恢复，调用前两期业务服务 |
| 部署 | Linux 服务器、Docker Compose；数据库与对象存储可使用托管服务 | 初期用少量组件部署，设置 HTTPS、持久化数据及备份，按实际负载扩容 |

选择依据：

- [Vite 官方指南](https://vite.dev/guide/) 提供 React 与 TypeScript 项目模板；[Ant Design 官方文档](https://ant.design/docs/react/introduce/) 提供 React 组件。本项目以表单、列表、详情和确认流程为主，适合采用这类前端组合。
- [FastAPI 官方文档](https://fastapi.tiangolo.com/features/) 说明其支持 OpenAPI 和 Pydantic 数据校验，可用于统一前后端接口及模型输出的数据结构。Python 后台也便于共享材料处理与后续 Agent 相关代码。
- [pgvector 项目文档](https://github.com/pgvector/pgvector) 说明可以在 PostgreSQL 中保存向量并结合全文检索。当前规模先统一管理案例数据与向量，降低组件数量；具体召回质量仍以业务样本验证。
- [Celery 官方文档](https://docs.celeryq.dev/en/stable/getting-started/introduction.html) 描述了独立工作进程与 Redis 等消息代理的任务队列模式。采用它处理需要重试的耗时工作时，业务侧仍须实现任务状态、幂等和失败处理；[FastAPI 后台任务文档](https://fastapi.tiangolo.com/tutorial/background-tasks/) 也区分了进程内轻量任务与 Celery 这类任务工具的适用场景。
- [LangGraph 官方文档](https://docs.langchain.com/oss/python/langgraph/overview) 描述了状态与流程控制、持久化执行和人工介入能力，符合第三期“排查、等待补充、继续执行”的需求。运行恢复需要实际配置持久化存储和恢复流程。

检索实现需要单独验证中文效果：错误码、编号及系统名称优先精确匹配，业务条件参与筛选，自然语言表达使用语义检索。PostgreSQL 默认全文检索不能直接视为已经具备适合本项目的中文分词能力；如需中文关键词召回，可先在应用层分词，再评估专用扩展。样本较少时先用简单查询和向量检索验证效果，再依据漏检记录改进。

模型的选择与业务代码分开。固定工作流加载版本化规则、调用模型，随后进行结构校验和业务校验。第三期工具调用模型另需验证工具选择、参数生成和多步排查能力；增加 LangGraph 不会自动使现有规则包生效，仍需在对应任务中显式加载。更换嵌入模型时需要验证向量兼容性，必要时重建索引。

账号优先接入公司已有登录体系，用户身份、业务范围与发布权限由后台统一校验。采集工具使用范围受限、可撤销的凭证访问平台；网页、采集端和后续 Agent 使用同一套业务权限规则。

Celery 工作进程运行在服务端 Linux 环境。微信桌面交互仍由用户电脑上的采集工具完成：本地工具主动拉取属于自己的任务或按本地计划执行，通过 HTTPS 上传材料和进度；服务端消费上传后的整理与索引任务。服务端定时器不能直接代替本地电脑操作微信。

第一期以固定业务流程交付，并把可复用业务能力独立封装。接口契约、数据版本、规则版本和评估记录纳入首期开发。第二期接入采集工具，第三期增加 LangGraph 编排与工具适配；每期按真实样本验证后再扩大范围。

**前两期必须落实的第三期衔接要求。**

第三期规划为自建业务排查 Agent：根据问题动态追问、选择工具、查询资料并推进多步排查。前两期以固定后台流程运行，同时把业务能力、数据和规则做成可复用的基础。第三期在这些能力上增加任务编排，减少重写案例库和收录流程的工作；具体 Agent 运行方式和工具适配仍需届时实现与验证。

| 基础要求 | 第一期交付 | 第二期补充 | 第三期复用方式 |
| --- | --- | --- | --- |
| 能力通过接口提供 | 案例搜索、案例与来源读取、材料导入、草稿保存、反馈提交；写入接口有明确状态和权限校验 | 采集任务创建、进度查询、结果导入，支持重复请求与失败重试 | 为已有接口增加工具描述和输入输出约束，供 Agent 调用 |
| 数据保存完整 | 问题、案例、来源、草稿和分析记录分别保存，使用稳定编号相互关联；保留条件、验证结果和修改版本 | 保存采集批次、来源群、消息时间与顺序、附件、覆盖范围及缺失说明 | Agent 按编号补充上下文、核对证据和继续跟进问题 |
| 规则独立维护 | 收录、分析与追问规则在后台独立维护；输出采用约定的数据结构；分析记录关联规则和模型版本 | 采集材料转换为同一套业务数据格式，渠道适配与案例整理规则分开 | 将已有规则包用于 Agent 任务，沿用输出校验和业务规则 |
| 积累评估样本 | 保存输入、返回的候选案例、最终引用、建议、用户反馈、人工修正及耗时和调用成本 | 增加漏采、重复、附件缺失和上下文分组错误的评估样本 | 在同一套业务问题和权限条件下比较固定流程与 Agent 的效果 |

接口需要围绕可独立调用的业务动作设计。例如“分析问题”可以是网页使用的完整流程，同时“搜索案例”“读取原始依据”“保存草稿”应可单独调用，便于 Agent 后续按需要组合。接口返回案例编号、来源编号、适用条件和验证状态等结构化字段，不能只返回一段供页面展示的答案。

这些接口可以由一个后台应用实现，内部业务逻辑可封装为独立服务函数；第三期再接入 Agent 工具调用。接口鉴权、数据访问范围、发布条件和状态转换由服务端执行。一次工具调用的权限应继承实际使用者或任务被授予的权限范围。

每次分析使用运行编号关联原始输入、补充信息、检索结果、来源版本、模型输出和人工反馈。引用定位到当时使用的来源版本，避免原文或案例修订后无法核对历史回答。原始材料、业务数据和模型运行记录分别存储，按资料保留策略维护，不把聊天会话或模型记忆当作唯一数据来源。

Skill 规则用于指导模型如何完成任务；必须执行的约束通过代码和数据校验保证。例如“未经确认不能标为已验证”“重复请求不新增相同草稿”“用户不能读取其他业务的材料”，应由后台保证执行，不能只写在提示词里。

第一期验收时增加以下检查：

- 脱离网页，使用相同身份调用接口，能够完成导入材料、检索案例、读取来源和保存草稿。
- 固定工作流通过上述可复用能力完成任务，页面负责输入与展示；业务流程在后台运行。
- 每条草稿和答案可以追溯到输入材料、所用来源版本及规则版本，人工修改保留记录。
- 重复保存请求不会生成重复草稿，发布和验证状态由后台检查，权限同时覆盖检索结果与原始附件。
- 已建立固定评估样本和人工确认的参考结论，保留失败样本，能够按相同资料与评分标准复盘；模型输出允许变化，不要求逐字一致。

第二期验收时增加以下检查：

- 手动录入与自动采集进入相同的材料、案例和规则体系；新增采集渠道无需重写提取和问答流程。
- 可通过任务编号查询采集范围、进度、结果和失败原因；重试可继续处理，并能核对是否存在缺失。
- 能将采集错误与整理、检索和回答错误分别定位，避免消息未采集成功却被误判为模型没有理解。

开发排期应包含上述基础工作。它们是前两期可验收的交付内容，并非等到第三期再补建的建议项。

**第二期：通过 Skill 编排微信聊天收集。**

第二期目标是减少手动复制整理：业务同事主动选取一段聊天，或让本地采集工具读取指定业务群的可获取记录，再由 Skill 编排分类、提取和案例草稿生成。实现由“本地采集工具＋任务运行器＋Skill＋平台接口”共同承担，单独的规则文件不会自动获得微信数据或持续运行。

本地采集工具运行在已登录微信的电脑上，获取用户选定的内容；任务运行器负责手动触发或定时执行；Skill 规定如何组织上下文、识别业务问题和关联历史案例；平台接口负责接收材料、去重、保存草稿和权限检查。普通网页需要本地工具配合，不能自行读取电脑里的微信内容。

| 阶段 | 用户体验 | 实现路线 | 验证重点 |
| --- | --- | --- | --- |
| 第二期前半段：一键收集 | 选中聊天并转交采集工具，平台自动生成待确认草稿 | 接收客户端可导出的聊天文件，解析文字和附件，通过平台接口导入 | 时间、发送人、消息顺序、图片引用是否正确保留 |
| 第二期后半段：指定群定时采集 | 设置采集群和周期，查看每次运行结果与新增草稿 | 本地运行器驱动已验证的桌面采集适配器，增量处理新材料 | 是否漏采、重复，客户端变化后能否发现失败，离线后能否恢复 |

可供验证的技术线索：macOS 项目 [Dukou](https://github.com/qzz0518/Dukou) 说明可接收微信合并转发的聊天文件，并提供实验性的批量操作；其文档也记录了部分账号无法通过界面控件自动采集的限制。Windows 工具 [wxauto](https://docs.wxauto.org/docs/install.html) 说明使用 Windows UI Automation 读取已登录桌面微信的界面消息，并列出支持版本。上述内容来自项目维护者文档，尚未在本项目或用户设备上实测，也不代表微信官方提供聊天采集 API。

建议先验证目标设备的“一键收集”路线，再决定是否开发定时采集。桌面工具能够读到的记录范围，不等于账号全部历史记录；缺失、未加载或无法解析的内容应明确标记。微信备份文件也不能直接假定为可解析的文本导出文件，需要验证具体输入格式。

采集范围绑定明确的业务群与时间范围；同名群需要额外确认对应关系。只将选定范围的材料送入平台，原始材料沿用业务权限。一次运行记录来源、实际覆盖时间、读取条数、导入条数和失败原因，使维护人能够判断是否完整。

重复导入优先按稳定消息标识处理；没有稳定标识时，结合来源、发送人、时间、内容及相邻消息核对，不能只按文本相同就删除，因为群里可能真实出现重复发言。增量采集保留少量重叠窗口，并在内容成功入库后推进采集进度。

AI 按问题及上下文组织材料，后续出现的解决结论关联到原问题；信息不足时保留为待补充记录。自动收集只生成材料和草稿，已验证状态仍以处理人的实际确认结果为准。

第二期先在一个业务群做小规模验证：人工对照指定时间段，检查消息顺序、上下文和附件；验证重复采集不生成重复案例，采集中断后能够重试。完成这些检查后，再评估多群和定时运行。定时任务需要采集电脑在线、微信保持可用，以及相应运行方式所需的桌面会话条件。

可用于提案的第二期文案：“在首期案例库和辅助问答上线后，平台将增加微信聊天辅助收集能力。通过本地采集工具与统一 Skill，业务同事可以将选定聊天一键转为案例草稿；在完成客户端兼容性和采集完整性验证后，进一步支持指定业务群的定时增量收集，减少经验整理的人工投入。”

**第三期：自建业务排查 Agent。**

当真实问题频繁需要动态追问、跨工具查询或根据查询结果继续排查时，启动 Agent 试点。目标是在已有能力上增加自主选择下一步的任务编排，由应用后台管理运行状态、工具权限、重试和停止条件。

| 交付内容 | 具体范围 | 验收重点 |
| --- | --- | --- |
| 工具接入 | 将已有案例、来源、草稿和采集查询接口适配为 Agent 工具，按实际需求增加业务只读查询 | 工具可以沿用已有服务逻辑、数据和权限，错误返回明确 |
| 多步任务 | 根据缺失条件追问，按结果选择检索或查询步骤，支持等待用户补充后继续 | 不同轮次围绕同一问题推进；等待、失败、取消和完成状态可见 |
| 运行控制 | 设置单次任务的步骤、时间和费用上限，记录工具调用过程 | 达到上限或外部查询失败时能够停止，保留已取得的证据并说明未完成部分 |
| 案例整理 | 将本次排查过程和用户确认结果整理成案例更新草稿 | 继续沿用草稿确认与发布流程，保持原始依据和验证结果可追溯 |
| 效果对比 | 用前两期积累的固定样本和真实任务比较效果 | 比较有用建议比例、证据正确性、完成时间、费用和人工介入次数 |

示例流程为：同事描述“已扣款但订单待支付”；Agent 追问缺失的订单信息；通过已接入的查询工具核对状态；检索并比较历史案例；给出有来源的排查建议；等待处理人反馈后生成案例更新草稿。未接入的业务数据源需要另行开发工具，Agent 本身不会自动获得访问能力。

先在少量业务和任务上验证，使用相同的数据版本、权限和评分标准与原固定流程比较，再逐步扩大使用范围。自动执行退款、修改订单等业务操作，另行定义操作接口、业务条件和必要的确认流程。

可用于提案的第三期文案：“第三期建设业务排查 Agent，复用前两期的案例库、采集能力、业务接口和 Skill 规则，支持动态追问、工具选择及多步排查。前两期同步落实接口、数据、规则和评估基础，使第三期主要围绕任务编排、工具接入与效果验证展开。”

**落地前需要明确的事项。**

开始实施时需要确定首个试点业务、知识维护人、团队账号来源、可使用的模型服务和部署位置，以及不同业务之间的资料可见范围。这些事项不影响当前方案讨论，但会影响最终技术选型和排期。

建议首先选择一个“问题出现频繁、处理结论相对明确、已有同事愿意维护”的业务场景，用真实记录验证从收录到复用的完整过程。
