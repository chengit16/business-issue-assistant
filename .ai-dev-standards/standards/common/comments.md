# 中文代码注释规范

本文件是各技术栈共用的注释要求；必须与对应技术栈的“中文注释规范”章节一起执行。适用于新增代码及实际修改职责、行为、契约的代码，历史内容按本次范围渐进补齐。

## 意图、维护与例外

- 新增或修改的注释使用中文，说明目的、业务规则、设计原因、边界、异常及对调用方的影响。注释必须与真实实现一致，代码变化时同步更新，不能以注释代替清晰命名和职责整理。
- 自解释赋值、私有简单方法不逐行注释。公开接口的用途说明不能只是翻译名称；字段不重复类型已表达的信息。生成文件、第三方代码、许可证、协议固定文本与工具指令保持原格式；需要改变生成内容时修改生成源。
- TODO/FIXME/HACK 必须包含责任人或角色、日期和退出条件，例如：`TODO(后端维护者, 2026-11-16): 所有旧记录迁移并验证后移除兼容分支。`
- 不写入秘密、无法验证的承诺、临时推测或已过时的说明。示例中的业务前提仅用于演示注释写法，采用时必须替换为真实约束。

## 必须说明的流程

三个及以上业务步骤、多个顺序依赖的异步或外部调用，以及权限、工作区隔离、默认拒绝、上下文切换、竞态、缓存失效、状态转换、摘要核对、并发锁、原子写入、事务、幂等、重试、失败兜底、敏感信息处理和历史兼容，必须在职责最近处解释原因与边界。

线性流程必须用连续编号标注业务阶段：TS/JS 使用 `// 1. ...`、`// 2. ...`，Python 使用 `# 1. ...`、`# 2. ...`。一个阶段覆盖完整逻辑块；非线性规则说明限制、拒绝、降级或必须保留的原因，不强行编造顺序。

| 函数有效代码行 | 注释与拆分要求 |
| --- | --- |
| 少于 30 | 不因长度强制分段；高风险规则仍必须说明。 |
| 30～59 | 存在两个以上控制流、异步、事务、存储或外部调用阶段时，连续编号说明主要阶段。 |
| 60～99 | 连续编号划分主要流程，通常不少于三个阶段，并评估拆分。 |
| 100 及以上 | 默认拆分；确需保留时写明“长函数保留原因：”，继续按业务阶段说明。 |

有效代码行不含签名、docstring、空行、注释、纯类型及仅用于排版的行；JSX 中有实际渲染或条件含义的行计入。行数不能替代业务判断，也不能通过无语义转发函数或模板注释规避。保存点、锁、竞态、临界值及防误删限制可用行内注释解释。

## 完成检查

1. 核对新增与实际修改的文件头、公开声明、字段和复杂流程，按技术栈表格检查最低说明。
2. 核对阶段编号、有效行数及长函数保留理由；检查注释是否解释实际约束，是否与调用方和契约一致。
3. 当前工具包尚未提供注释自动检查器；这些要求作为开发和评审约束执行。将来结构检查只验证可确定的文件头、声明和阶段标记，不能证明语义正确或替代代码评审。
